# Data Pipeline Operations Runbook

## Safety and identity

These procedures apply only to the existing full DEV platform in
`ap-southeast-2`. Use the MFA-authenticated Human -> Operator -> DataEngineer
role chain. Keep temporary credentials in process memory, never in a file. Do
not delete landing, quarantine, control or Iceberg objects during a drill.

Every drill object must be under `batch/v5-drill/<run_id>/`, where `run_id` is
generated by `scripts/v5/operational_drill.py`. The CLI is dry-run by default;
AWS writes require both the `execute` command and `--execute`.

## Batch pipeline or missing-input failure

**Symptom:** `insurance-dev-batch-claim-lakehouse` execution is `FAILED`, or a
stage failure alarm is active.

1. Identify the execution and failed state without exposing input data:

   ```powershell
   aws stepfunctions list-executions --region ap-southeast-2 --state-machine-arn arn:aws:states:ap-southeast-2:199476069493:stateMachine:insurance-dev-batch-claim-lakehouse --status-filter FAILED --max-results 10
   aws stepfunctions get-execution-history --region ap-southeast-2 --execution-arn <execution-arn> --reverse-order --max-results 25
   ```

2. Read the exact stage audit at
   `s3://aip-insurance-dev-control-dev01/control/v2/pipeline_runs/<run_id>/`.
   A missing-object drill should contain `bronze.json` and
   `bronze-failure.json` with `NoSuchKey` evidence.
3. For deterministic input/IAM/schema errors, fix the source or permission
   before replay. For a transient service error, retry only after checking the
   original execution is terminal; use at most three operator attempts.
4. Upload a corrected unique object and allow EventBridge to start the normal
   workflow. Never overwrite or remove the failed evidence.
5. Confirm all three stages succeeded and run the reconciliation/Athena checks
   in `docs/v5-operational-drill.md`.

Escalate if recovery needs an Iceberg snapshot deletion, a new service, a broad
IAM grant, or three transient attempts fail.

## Glue job failure

**Symptom:** Step Functions reports a failed `RunBronze`, `RunSilver` or
`RunGold` task.

```powershell
aws glue get-job-run --region ap-southeast-2 --job-name <job-name> --run-id <glue-run-id> --predecessors-included
aws logs filter-log-events --region ap-southeast-2 --log-group-name <log-group> --filter-pattern ERROR --limit 50
```

Capture job name/run ID, stage, sanitized error, source key and pipeline run ID.
Correct the source/script/IAM issue through the normal PR/Terraform path when
needed. Do not manually publish Silver or Gold around a failed prior stage.
Replay through Step Functions so ordering and audit boundaries remain intact.

## Glue Data Quality failure

**Symptom:** Silver fails with `DQGateFailure`, or a run audit reports a failed
dataset rule.

```powershell
aws glue get-data-quality-result --region ap-southeast-2 --result-id <result-id>
aws s3 ls s3://aip-insurance-dev-control-dev01/control/v2/data-quality/ --recursive
```

Identify failed rule names and counts, not customer values. Dataset DQ failure
must prevent Silver/Gold promotion; compare trusted counts with the pre-run
baseline. Correct the synthetic/source rows, upload a new uniquely named file,
and verify DQ score `1.0` for the recovered candidate. Do not weaken a rule to
make the drill pass.

## Quarantined data handling

**Symptom:** audit `rejected_count > 0` or objects exist below
`quarantine/v2/batch/claim/<run_id>/`.

```powershell
aws s3 ls s3://aip-insurance-dev-quarantine-dev01/quarantine/v2/batch/claim/<run_id>/ --recursive
aws s3 cp s3://aip-insurance-dev-control-dev01/control/v2/pipeline_runs/<run_id>/silver.json - --region ap-southeast-2
```

Restrict this work to DataEngineer because quarantine may contain source PII.
Inspect failed rule metadata and only the minimum record fields. Retain the
original quarantine evidence; create a corrected new source object rather than
editing quarantine. Verify rejected claim IDs are absent from trusted Gold.

## Batch replay and idempotency

After corrected full-snapshot recovery succeeds, upload the byte-identical
`broker_claims_v5_duplicate_replay.csv` generated by the toolkit to its unique
V5 key. Content SHA-256, not the object name, is the logical file identity.
Expected audit status is `DUPLICATE`, with `output_count=0`,
`duplicate_count=input_count`, and no Gold row-count or key-uniqueness change.
If counts change, stop replays and escalate as an idempotency regression.

## CDC replay and recovery

The CDC job rebuilds current state from retained DMS CSV history. Do not apply
the Batch reconciliation equation to CDC. Select an existing `oltp/` object
read-only, then start the existing CDC state machine with the toolkit's
`cdc-replay` scenario. This does not mutate RDS or restart DMS.

Expected results are Bronze history deduplication, latest I/U selection, D
tombstone removal, and the same Gold current-state row/key counts as before.
Compare `control/v2/pipeline_runs/<run_id>/{bronze,silver,gold}.json` and Athena
results. Escalate rather than deleting DMS files, resetting replication state,
or rewriting Iceberg history. The pre-existing stopped/failed DMS task status
is a documented limitation and is not repaired by this runbook.

## Alarm and CI/CD handoff

For an active alarm, capture alarm name/state-change time/reason, execution ARN,
run ID and stage before recovery. Follow the infrastructure alarm runbook for
SNS delivery. Deployment/PROD approval failures use the V4 CI/CD runbook; data
operators must not bypass protected `main`, manually edit AWS job scripts, or
apply PROD platform resources.
